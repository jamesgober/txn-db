# txn-db v1.1.0: Correctness release

**Fixes four correctness bugs in the commit path and makes point reads scale.**
A durable commit that failed at the log could be read and then lost; the
read-only anomaly survived `serializable`; a panic inside a custom store stopped
every later commit from becoming visible; and `commit` could return before its
own write was visible. All are fixed. The release adds `TxnError::TooLarge` and
`VersionStore::try_commit_ordered`. Nothing breaks: the commit-log format is
unchanged, logs written by 1.0 replay as before, and the MSRV stays 1.85.

## What is txn-db?

A multi-version concurrency control (MVCC) transaction engine: the layer that
turns a key-value store into a transactional database. Readers get a stable
snapshot without blocking writers, and writers detect conflicts at commit time.
The version store is a trait, so the engine composes on top of any backend that
keeps timestamped versions.

## What's fixed

### A failed durable commit was visible, then lost

With the `durability` feature, a commit's writes were applied in memory before
its record was appended to the log. When the append or sync failed, the code
still released the commit's timestamp, so every reader saw writes that were
never logged. Other transactions could read them and commit durably, and after
a restart the source write was gone while the dependants remained. A single
transaction over `wal-db`'s 64 MiB record limit always took this path; a full
disk did the same for every commit.

Now:

- A commit whose record would exceed the limit is refused with the new
  `TxnError::TooLarge { len, limit }` before anything is applied or logged. The
  database stays usable. The limit is 64 MiB per commit record; the encoded size
  is 13 bytes, plus for each write 5 bytes and the key, plus for each value 4
  bytes and the value.
- If the append or sync fails, the commit's writes are removed before its
  timestamp is released, so no reader can see them, and the commit returns
  `TxnError::Durability`.
- After such a failure the database refuses every later commit with
  `TxnError::Durability` until it is reopened, since the log file's state is in
  doubt. `is_fatal` now means what it says. A commit reported this way may still
  appear after reopening if its record reached the disk before the sync failed.

### The read-only anomaly survived `serializable`

A commit took its timestamp before it got the store's shard locks. A commit D
could take timestamp 3, wait on a lock held by a commit W with timestamp 4, and
apply after W. When W had read a key D writes, W precedes D in any serial order,
but a snapshot cut after D finished and before W did showed D without W. This is
the read-only anomaly of Fekete, O'Neil and O'Neil, and it occurred with all
three transactions serializable.

Commits now take their timestamp while the store holds their locks, so commits
that touch overlapping keys apply in timestamp order. The serialization order of
serializable transactions is their commit-timestamp order, and every snapshot
shows a state of that order.

- `MemoryStore` takes the timestamp inside its shard locks, after validation.
- A custom store gets the same guarantee through the default
  `VersionStore::try_commit_ordered`. It holds a process-wide reader-writer lock
  across the timestamp and `try_commit`: shared for commits without a read set,
  exclusive for serializable commits that validate one. A store with its own
  locking can override `try_commit_ordered` to take the timestamp under those
  locks instead.

The documentation now describes the serializable mode as what it is: optimistic
read-set validation (backward validation), not SSI. It can abort transactions
that SSI would let commit, and it covers serializable transactions; a
snapshot-isolation writer can still form write skew with them.

### A store panic stopped the read watermark for good

If `VersionStore::try_commit` panicked, its timestamp was never released. The
watermark stopped, so every later commit returned `Ok` and was never visible,
memory grew per commit, and `Db::put` of a key it had already written looped
forever. The timestamp is now held by a guard that releases it on every path out
of the commit, including unwinding, so a panic costs one transaction. The
`try_commit` contract states that a store must not panic after it has started to
apply a batch.

### `commit` returned before its write was visible

Visibility waits for every earlier timestamp to finish. A commit that returned
while an earlier one was still in flight was not yet visible, so a thread could
commit and then fail to read its own write. `commit` now returns once the write
is visible: it spins briefly, then yields, then parks until the earlier commits
finish. `Db::begin`, `Db::snapshot`, `Db::get`, and `Db::last_committed` include
every commit that has returned.

`Db::put` and `Db::delete` used to retry in a tight loop against a conflicting
version that was not visible yet. They now wait until the commit they lost to is
visible before retrying, and return the conflict after 10,000 conflicts in a row
instead of looping without bound.

## Performance

The live-reader registry that garbage collection consults was one mutex-guarded
map, taken twice by every transaction, snapshot, and `Db::get`, so point reads
got slower in total as threads were added. It is now 32 slots on separate cache
lines, and `Db::get` no longer clones the database handle per read.

A/B in one process against 1.0.1, alternating rounds, median, total Mops/s. The
host was fully loaded by unrelated work during these runs, so multi-threaded
results are noisy; `docs/PERFORMANCE.md` has the full table with ranges.
Multi-key transactions on several threads moved in both directions across runs,
within the noise. The commit timestamp is now taken inside the shard locks, one
contended atomic increment longer per multi-shard critical section, which is
the price of the ordering serializable isolation needs.

| Workload | 1.0.1 | 1.1.0 |
|----------|------:|------:|
| `Db::get`, 1 thread | 11.5 | 15.2 |
| `Db::get`, 8 threads | 4.1 | 17.2 |
| `Db::put`, one hot key, 4 threads | 0.40 | 1.10 |
| `Db::get`, 16 threads | 3.1 | 24.1 |

## Other changes

- `Db::open` collects the replayed history once after recovery, so a reopened
  database holds the current value of each key instead of every logged version.
- A serializable read of a key already in the read set no longer allocates.
- The conflict message no longer says "write-write" for a read-set conflict.
- Stale status text in the crate docs, README, and `MemoryStore` docs is fixed,
  and the `VersionStore::try_commit` contract states that calls can arrive out
  of timestamp order.
- The commit log is still never truncated, and `Db::open` replays every record;
  this is now documented.

## Tests

Each fix has a regression test that fails on 1.0.1: `tests/ordering.rs` covers
the read-only anomaly (through the default ordering and through `MemoryStore`),
the panicking store, read-your-writes after commit, the oversize durable commit,
and replay collection. A unit test injects a log-append failure. A new loom
model cuts a read-only transaction between two overlapping serializable commits
and checks that it sees a serial state; it fails if the timestamp is taken
before the locks. The loom CI job now runs with `--features serializable`.

## Breaking changes

**None.** `TxnError` is `#[non_exhaustive]`, so `TooLarge` is additive, and
`try_commit_ordered` is a provided trait method, so existing `VersionStore`
implementations compile unchanged. `cargo semver-checks` against 1.0.1 passes
all 196 checks with no breaking change.
