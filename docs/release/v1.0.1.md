# txn-db v1.0.1 — Patch: retry metadata through `ForgeError`

**Bug fix.** `TxnError` now reports a transaction conflict as retryable through
the `error_forge::ForgeError` trait, not only through its inherent method. No API
change; the commit-log format is unchanged.

## What is txn-db?

A multi-version concurrency control (MVCC) transaction engine: the layer that
turns a key-value store into a transactional database. Readers get a stable
snapshot without blocking writers, and writers detect conflicts at commit time.
The version store is a trait, so the engine composes on top of any backend that
keeps timestamped versions.

## What's fixed in 1.0.1

### `ForgeError::is_retryable` was always `false`

`TxnError` has an inherent `is_retryable` that returns `true` for `Conflict`, but
its `impl ForgeError for TxnError` did not override the trait's `is_retryable`,
so the trait default (`false`) applied. The two answers disagreed:

```rust
use error_forge::ForgeError;
use txn_db::TxnError;

let err = TxnError::conflict(8);
assert!(err.is_retryable());                                // inherent: true
assert!(<TxnError as ForgeError>::is_retryable(&err));      // 1.0.0: false, 1.0.1: true
let dyn_err: &dyn ForgeError = &err;
assert!(dyn_err.is_retryable());                            // 1.0.0: false, 1.0.1: true
```

Code that held the error as a `&dyn ForgeError` or `Box<dyn ForgeError>`, or
went through `error-forge`'s generic retry and recovery helpers, never retried a
transaction conflict. Code that called `TxnError::is_retryable` directly, such as
the retry loops in the README and examples, was not affected.

The trait method now delegates to the inherent method, so there is one
definition of retryability and the two cannot drift apart. `Conflict` is
retryable; `Store` and `Durability` are not. `is_fatal` was already correct
(`true` only for `Durability`) and is unchanged.

New tests call `is_retryable`, `is_fatal` and `kind` through
`<TxnError as ForgeError>` and through `&dyn ForgeError` for every variant, and
box a real commit conflict as `Box<dyn ForgeError>`. The variant list is checked
by an exhaustive `match`, so a new variant cannot be added without being covered.
